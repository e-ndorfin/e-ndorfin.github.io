From expiring orders to one active recipe

PR #20 reshapes Overcooked V3’s recipe target: instead of maintaining a partially implemented queue of expiring orders, the environment keeps one bit-encoded active recipe and can choose a new one after a successful delivery.

1. Background

In Overcooked V3, a recipe is the soup agents are currently supposed to deliver. A layout supplies possible_recipes, such as three onions [0, 0, 0] or three tomatoes [1, 1, 1]. At runtime, the chosen recipe is compressed into an integer bit pattern and stored in state.recipe.

Mental model
The layout is the menu; state.recipe is today’s order. The menu is static configuration. The active order is dynamic episode state and is what delivery checks and observations read.

The prior mismatch

main contains an optional order-queue subsystem: fixed arrays for order types, expirations, and active slots; per-step generation; expiry penalties; and a separate PRNG split. But the actual cooking and delivery path still compares a delivered soup with the single state.recipe. That leaves two competing concepts of “the target.”

Before: queue machinery

  • May generate queue entries each step
  • Counts down expiry timers
  • Penalizes expired entries
  • Delivery still uses state.recipe

PR #20: active recipe

  • Samples from the layout menu
  • Uses optional explicit probabilities
  • Resamples only after correct delivery
  • One value drives checks and observations

The PR therefore does two related jobs: it adds random active-recipe sampling, and it removes the live order-queue pipeline. Legacy queue arrays remain in State as inert, fixed-size fields—preserving the state shape while deleting behavior.

2. Intuition

Suppose the layout offers two recipes in this exact order:

IndexRecipeMeaningProbability
0[0, 0, 0]Three onions0.7

With recipe_probs=[0.7, 0.3], reset samples an index from that distribution and encodes the corresponding list. If probabilities are omitted, the sampling is uniform. The probability list is positional: swapping the layout recipes without swapping the probabilities changes the meaning.

env = OvercookedV3(
    layout="random_recipe_demo",
    enable_random_recipe=True,

3. Code

A. Public configuration validates the distribution

The constructor adds enable_random_recipe and recipe_probs at overcooked.py:86–88. Validation at overcooked.py:481–516 rejects non-numeric, non-1D, wrong-length, non-finite, negative, or non-normalized inputs before converting them to a JAX array.

# Conceptual contract
len(recipe_probs) == len(layout.possible_recipes)
all(isfinite(p) and p >= 0 for p in recipe_probs)
sum(recipe_probs) ≈ 1.0

This is constructor-time Python validation, which is appropriate because configuration errors should fail early rather than surface inside a JIT-compiled step.

B. One helper owns recipe selection

initialization.py:15–24 centralizes selection in sample_recipe. It uses jax.random.randint for uniform selection or jax.random.choice(..., p=recipe_probs) for weighted selection, then calls DynamicObject.get_recipe_encoding.

recipe_idx = uniform_index(key) if probs is None else weighted_index(key, probs)
recipe = possible_recipes[recipe_idx]
return encode_recipe(recipe)

C. Reset always chooses an active recipe

reset.py:63–64 splits the reset key and calls the helper. This means multiple-recipe layouts can vary at episode start regardless of whether between-delivery switching is enabled. The encoded result enters State at reset.py:105.

D. The delivery step conditionally changes the target

Agent interactions run through a JAX lax.scan. Each interaction reports whether it produced a correct delivery; the scan ORs those flags together (agent_step.py:279–282). After interactions and pot updates, lines 320–335 use lax.cond:

sample_new_recipe = new_correct_delivery & config.enable_random_recipe
new_recipe = lax.cond(
    sample_new_recipe,
    lambda key: sample_recipe(key, config),
    lambda _: state.recipe,
    recipe_key,
)

The replacement state carries both recipe=new_recipe and new_correct_delivery. Because the normal step pipeline builds observations afterward, the recipe-indicator encoding reflects the newly sampled target immediately.

E. Queue behavior is deliberately removed

The PR deletes systems/orders.py, removes queue configuration and the per-step queue call, and stops splitting each step key into agent and order keys. The three queue arrays remain zeroed using DEFAULT_MAX_ORDERS and are documented as legacy inert fields.

Rebase/conflict resolution and a clean-environment test run are still required.

Trade-offs and edge cases

  • A sampled next recipe may equal the previous one; “resample” does not guarantee a change.
  • Correct-delivery events from multiple agents in the same step collapse to one boolean, so at most one new recipe is sampled per step.
  • Probability order is coupled to layout.possible_recipes; it is not keyed by recipe value.
  • Keeping inert queue arrays avoids immediate structural churn, but leaves cleanup debt and potentially confusing fields.
  • The PR’s removal of queue APIs is a behavioral/API break for callers that enabled or invoked that subsystem.
